AWS SDKのHTTPクライアントを差し替えて、テストのプロセスの中で状態を持つAWSを動かすモック `wasmo` を作りました。
Dockerもポートも別のプロセスも使わずに、DynamoDBに書いた値が次の `GetItem` で返り、S3に置いたオブジェクトが `ListObjects` の結果に入ります。

パッケージはGoとJavaScriptとJVMと.NETとPythonとRubyの6言語にあり、どのパッケージでもRustで書いた同じWebAssemblyのモジュールが応答を返すので、言語が違ってもモックの振る舞いは同じです。

リポジトリは [conao3/wasm-wasmo](https://github.com/conao3/wasm-wasmo) で、ライセンスはApache-2.0です。
この記事では各言語のレジストリに公開している0.1.1を使います。

同じくAWSのモックの [bunsai](https://s.conao3.com/blog/2026/2653f0) は別のプロセスのサーバーとしてポート4566で待ち受けますが、wasmoはテストのプロセスの中で動きます。

# 使ってみる

Pythonでは `pip install wasmo boto3` で入れます。
`wasmo.mock_aws()` の中で作ったboto3のクライアントは、リクエストをモックに送ります。
次のスクリプトは1つのモックの中で動き、S3のバケットにオブジェクトができたらLambdaの関数を呼び、その関数がDynamoDBのテーブルにキーを書きます。

```python
import boto3
import wasmo

with wasmo.mock_aws() as aws:
    s3 = boto3.client("s3")
    ddb = boto3.client("dynamodb")
    lam = boto3.client("lambda")

    ddb.create_table(
        TableName="uploads",
        KeySchema=[{"AttributeName": "key", "KeyType": "HASH"}],
        AttributeDefinitions=[{"AttributeName": "key", "AttributeType": "S"}],
        BillingMode="PAY_PER_REQUEST",
    )

    def on_upload(event, context):
        for record in event["Records"]:
            key = record["s3"]["object"]["key"]
            boto3.client("dynamodb").put_item(
                TableName="uploads", Item={"key": {"S": key}}
            )
        return {"ok": True}

    aws.register_function("on-upload", on_upload)
    fn = lam.create_function(
        FunctionName="on-upload",
        Runtime="python3.12",
        Role="arn:aws:iam::000000000000:role/lambda",
        Handler="index.handler",
        Code={"ZipFile": b"unused"},
    )

    s3.create_bucket(Bucket="photos")
    s3.put_bucket_notification_configuration(
        Bucket="photos",
        NotificationConfiguration={
            "LambdaFunctionConfigurations": [
                {"LambdaFunctionArn": fn["FunctionArn"], "Events": ["s3:ObjectCreated:*"]}
            ]
        },
    )

    s3.put_object(Bucket="photos", Key="cat.jpg", Body=b"...")
    print(ddb.get_item(TableName="uploads", Key={"key": {"S": "cat.jpg"}})["Item"])
```

```console
$ python demo.py
{'key': {'S': 'cat.jpg'}}
```

wasmoは `CreateFunction` に渡したコードを実行せずに、同じ関数名で `register_function` に登録したPythonの関数を呼びます。
S3の通知は `PutObject` の呼び出しの中で届くので、 `put_object` が返った時点でDynamoDBに項目があります。

wasmoはモックが次のリクエストを受け付けられる状態で登録した関数を呼ぶので、関数の中から同じモックにリクエストを送れます。
同じ流れをAWS SDK for JavaScript v3と `@conao3/wasmo` で書いても、 `GetItem` は同じ項目を返しました。

Intel Core Ultra 5 225Uの手元のPCでPythonのパッケージを測ると、プロセスの最初のリクエストはモジュールのコンパイルを含むので0.6〜1.0秒かかりました。

2回目からは1回あたり2ms以下でした。
モックを新しく作って最初の応答を受けるまでは9msなので、テストごとにモックを作り直せます。


# 仕組み

どの言語のAWS SDKもHTTPクライアントを差し替えられるので、wasmoはAWSの通信のプロトコルそのものを言語の境目にしています。

```text
各言語のAWS SDK
  └─ HTTPクライアントのアダプター (言語ごとに数百行)
       └─ WebAssemblyのランタイム (Go: wazero、JVM: Chicory、JS: 組み込み、Ruby: wasmtime-rb、Pythonと.NET: wasmtime)
            └─ wasmo.wasm (Rust、wasm32-unknown-unknown)
```

アダプターはSDKが組み立てたリクエストから、メソッドとURLとヘッダーのJSONと本文のバイト列を作ってモジュールの `wasmo_handle` に渡し、返ってきた応答をSDKに戻します。
署名とリトライ、チェックサムの検証と応答の解析はSDKが行うので、テストでも本物のAWSに向けたときと同じSDKのコードが動きます。

モジュールはWASIを使わずに、時計と乱数とLambdaの呼び出しの3つの関数をホストからimportします。
状態はWebAssemblyのインスタンスの中にあり、モックごとにインスタンスを1つ作るので、並列に動くテストどうしで状態は混ざりません。

Lambdaのハンドラを待つときは、モジュールは応答の代わりに `await` の印を返すので、アダプターは登録した関数を動かして結果を `wasmo_complete` に渡し、待つものが無くなるまでこれを繰り返します。

# bunsaiとの違い

bunsaiとwasmoはどちらもAWSのモックですが、動く場所が違います。

bunsaiはBunで書いたサーバーで、ポート4566でAWSのゲートウェイとダッシュボードを待ち受けるので、SDKのほかにAWS CLIやTerraformもエンドポイントを向ければ使えます。

サービスは146です。
bunsaiのLambdaはホストにあるPythonやRubyの言語のランタイムを起動して関数のコードをそのまま動かします。

wasmoはテストのプロセスの中で動き、SDKのHTTPクライアントだけを差し替えるので、テストはモックを作って使ったら閉じるだけです。

サービスは19です。
wasmoのLambdaは関数のコードを動かす代わりにテストの言語で登録した関数を呼びます。

wasmoのサービスの振る舞いは、実際のAWSに由来する期待値を持つbunsaiのparity fixtureを流して確かめていて、確かめ方は [READMEのConformanceの節](https://github.com/conao3/wasm-wasmo#conformance) にあります。

AWS CLIやTerraformから使いたいときと状態をダッシュボードで見たいときはbunsaiを、言語のテストの中で完結させたいときはwasmoを使います。


# 対応しているサービス

0.1.1は次の19のサービスに応答します。

-   認証と鍵と秘密の情報: STS、IAM、KMS、Secrets Manager、SSM Parameter Store
-   メッセージとストリーム: SQS、SNS、EventBridge、Kinesis、Data Firehose
-   データ: S3、DynamoDB、DynamoDB Streams
-   監視: CloudWatch、CloudWatch Logs
-   関数とAPI: Lambda、Step Functions、API GatewayのREST APIとHTTP API

サービスの間の配信もモックの中で動き、たとえば次の向きに届きます。

-   SNSからSQSとLambdaへ
-   EventBridgeからSQSとSNSとLambdaとStep Functionsへ
-   S3の通知からSQSとSNSとEventBridgeとLambdaへ

Step Functionsはステートマシンの定義をモックの中で解釈し、Lambdaを呼ぶタスクは登録した関数が返るまで待つので、 `StartSyncExecution` は関数を動かしたあとの出力を返します。
サービスごとに対応している操作と配信の向きの一覧は [READMEのCoverageの節](https://github.com/conao3/wasm-wasmo#coverage) にあります。

READMEではまだ開発の初期の段階としています。
リポジトリのテストではGoのアダプターが各サービスを細かく試し、ほかの5言語はサービスごとに1つ以上の通しのシナリオをSDKから試しています。
