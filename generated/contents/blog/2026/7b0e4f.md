Title: Hasuraが生成するSQLは長いが、遅いのは入れ子の一括取得だけだった
Date: 2026-11-17 01:42
Draft: true
Tags: hasura graphql postgresql performance


HasuraはPostgreSQLのテーブルからGraphQLのAPIを作るサーバーです。
resolverを書かずにAPIができるので気に入っています。
ただ、実行されるSQLを見ると短いGraphQLのクエリでも副問い合わせが何段も重なっていて、遅くならないのかが気になっていました。

そこで、Hasuraが生成するSQLと、同じJSONを返すように手で書いたSQLの速さを比べました。
記事を20件ずつ取るようなページ単位のクエリでは、差がありませんでした。
遅かったのは親と子を数万件まとめて取る入れ子のクエリだけで、手書きの2倍の時間がかかっています。
このクエリはroot fieldを分けて書き直すと2.5倍速くなりました。

比べたのはHasura GraphQL Engine v2.29.0とPostgreSQL 17.11です。


# 生成されるSQL

次のクエリは、新しい記事20件に、著者の名前とコメントの先頭5件を付けて取ります。

```graphql
query A {
  article(limit: 20, order_by: {published_at: desc}) {
    id
    title
    author { name }
    comments(limit: 5, order_by: {id: asc}) { body }
  }
}
```

[Explain API](https://hasura.io/docs/2.0/api-reference/explain/)にクエリを送ると、Hasuraが生成するSQLを見られます。
上のクエリは次のSQLになりました。
改行と字下げは私が足したものです。

```sql
SELECT coalesce(json_agg("root" ORDER BY "root.pg.published_at" DESC NULLS FIRST), '[]' ) AS "root"
FROM (
  SELECT row_to_json((SELECT "_e" FROM (SELECT
           "_root.base"."id" AS "id", "_root.base"."title" AS "title",
           "_root.or.author"."author" AS "author",
           "_root.ar.root.comments"."comments" AS "comments" ) AS "_e" ) ) AS "root",
         "_root.base"."published_at" AS "root.pg.published_at"
  FROM (SELECT * FROM "public"."article" WHERE ('true')
        ORDER BY "published_at" DESC NULLS FIRST LIMIT 20 ) AS "_root.base"
  LEFT OUTER JOIN LATERAL (
    SELECT row_to_json((SELECT "_e" FROM (SELECT "_root.or.author.base"."name" AS "name" ) AS "_e" ) ) AS "author"
    FROM (SELECT * FROM "public"."author"
          WHERE (("_root.base"."author_id") = ("id")) LIMIT 1 ) AS "_root.or.author.base"
  ) AS "_root.or.author" ON ('true')
  LEFT OUTER JOIN LATERAL (
    SELECT coalesce(json_agg("comments" ORDER BY "root.ar.root.comments.pg.id" ASC NULLS LAST), '[]' ) AS "comments"
    FROM (
      SELECT row_to_json((SELECT "_e" FROM (SELECT "_root.ar.root.comments.base"."body" AS "body" ) AS "_e" ) ) AS "comments",
             "_root.ar.root.comments.base"."id" AS "root.ar.root.comments.pg.id"
      FROM (SELECT * FROM "public"."comment" WHERE (("_root.base"."id") = ("article_id"))
            ORDER BY "id" ASC NULLS LAST LIMIT 5 ) AS "_root.ar.root.comments.base"
      ORDER BY "root.ar.root.comments.pg.id" ASC NULLS LAST
    ) AS "_root.ar.root.comments"
  ) AS "_root.ar.root.comments" ON ('true')
  ORDER BY "root.pg.published_at" DESC NULLS FIRST
) AS "_root"
```

GraphQLの入れ子1段が、SQLでは副問い合わせ1つになっています。
`author` や `comments` のrelationshipを1つたどるごとに、 `LEFT OUTER JOIN LATERAL` が1つ加わります。
JSONもSQLの中で作り、行を `row_to_json` で、配列を `json_agg` でJSONにします。
一番外側の `json_agg` の値が応答の配列です。


# SQLを1本にする設計

![img](../../../../resources/public/img/7b0e4f-flow.svg)

Hasuraにはresolverがありません。
[公式のドキュメント](https://hasura.io/docs/2.0/getting-started/how-it-works/index/)は、GraphQLのクエリをSQLにするコンパイラとしてHasuraを説明しています。
Hasuraが受け持つのはSQLへの変換までで、行の取得と結合とJSONへの整形は、PostgreSQLが1回の実行で行います。

resolverがフィールドごとにデータを取る作りでは、親の行の数だけ子のSQLを実行するN+1問題が起きます。
Hasuraの[設計の文書](https://github.com/hasura/graphql-engine/blob/master/architecture/live-queries.md)は、クエリ全体を1本のSQLにすればN+1問題がなくなり、データベースが全体を見て最適化できると書いています。
SQLが長いのは、クエリの全部をこの1本に入れているからです。


# 手書きのSQLとの比較

比較には、著者1万件、記事20万件、コメント100万件のデータを使いました。
外部キーの列にはindexを張っています。
HasuraとPostgreSQLはDockerのコンテナで動かし、CPUをそれぞれ2コアに制限しました。
ロールはadminで、行の権限は付けていません。

測ったクエリは3つです。

-   Aは「生成されるSQL」の節のクエリで、記事20件に著者とコメント5件を付けます。
-   Bは記事5万件に著者を付けます。
-   Cは著者2,000人に、その記事4万件と、記事のコメント20万件を入れ子で付けます。

手書きのSQLは、JOINと `json_build_object` で同じJSONを返すように書きました。
Aの手書きのSQLは次のとおりです。

```sql
SELECT coalesce(json_agg(json_build_object(
         'id', a.id, 'title', a.title,
         'author', json_build_object('name', au.name),
         'comments', c.comments) ORDER BY a.published_at DESC), '[]')
FROM (SELECT * FROM article ORDER BY published_at DESC LIMIT 20) a
JOIN author au ON au.id = a.author_id
LEFT JOIN LATERAL (
  SELECT coalesce(json_agg(json_build_object('body', x.body) ORDER BY x.id), '[]') AS comments
  FROM (SELECT id, body FROM comment WHERE article_id = a.id ORDER BY id LIMIT 5) x
) c ON true
```

どのクエリも、HasuraのSQLと手書きのSQLが同じJSONを返すことを確かめてから測りました。

# 一括取得が遅くなる仕組み

差の理由は実行計画から分かります。

HasuraのSQLでは、relationshipごとの副問い合わせを `LATERAL` で結合し、その副問い合わせの中に `LIMIT` か `json_agg` があります。
PostgreSQLはこの副問い合わせを、親の行ごとに子のテーブルを引くNested Loopで実行しました。
Aでは親が20行なので、indexを数十回引くだけで終わります。
Cでは、記事のテーブルを2,000回、コメントのテーブルを4万回引いていました。
次は、Cの `EXPLAIN (ANALYZE)` から、コストと時間の表示を省いて抜き出した行です。
`loops` は実行した回数です。

```text
->  Aggregate  (rows=1 loops=2000)
      ->  Nested Loop Left Join  (rows=20 loops=2000)
            ->  Bitmap Heap Scan on article  (rows=20 loops=2000)
            ->  Aggregate  (rows=1 loops=40000)
                  ->  Bitmap Heap Scan on comment  (rows=5 loops=40000)
```

手書きのSQLは、3つのテーブルをHash Joinで結合します。
コメントのテーブルを読むのは1回です。

Bが遅くならなかったのは、PostgreSQL 14で入った[Memoize](https://www.postgresql.org/docs/14/release-14.html)が、Nested Loopの内側の結果をキャッシュしていたからです。
5万件の記事に対して、著者のテーブルを引いたのは1万回でした。


# Hasuraの機能での書き直し

Cのような一括取得は、Hasuraの機能だけで速くできます。
Cは次のクエリです。

```graphql
query C {
  author(limit: 2000, order_by: {id: asc}) {
    id
    name
    articles {
      id
      title
      comments { body }
    }
  }
}
```

これを2つの書き方に直しました。

1つめは、入れ子をやめてroot fieldを3つ並べる書き方です。

```graphql
query D {
  author(limit: 2000, order_by: {id: asc}) { id name }
  article(where: {author_id: {_lte: 2000}}) { id title author_id }
  comment(where: {article: {author_id: {_lte: 2000}}}) { article_id body }
}
```

`comment` の `where` でrelationshipを使うと、SQLでは `EXISTS` の副問い合わせになり、PostgreSQLはHash Joinを選びました。
クライアントが `author_id` と `article_id` を使って入れ子を組み立てます。

2つめは、手書きのSQLを[Native Query](https://hasura.io/docs/2.0/schema/postgres/native-queries/)としてHasuraに登録する書き方です。
Community EditionでNative Queryを使えるのは、v2.28.0からです。
Hasuraは登録したSQLをCTEとして実行し、そのCTEの外側のSELECTでJSONにします。
記事とコメントは `json` 型の1つのフィールドになるので、その中の項目をGraphQLで選べなくなります。

# 書き直すクエリ

画面に表示するページ単位のクエリでは、生成されるSQLの長さは速さに影響しませんでした。
書き直す価値があるのは、エクスポートや集計のように、親と子を数万件まとめて取るクエリです。
そのクエリだけroot fieldを分けるかNative Queryにすれば、ほかのクエリはHasuraに任せたままにできます。
