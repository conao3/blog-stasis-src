I built `wasmo`, an AWS mock that replaces the HTTP client of the AWS SDK and runs a stateful AWS inside your test process.
You need no Docker, no open port, and no second process: a value you write to DynamoDB comes back from the next `GetItem`, and an object you put in S3 shows up in `ListObjects`.

wasmo ships packages for six languages: Go, JavaScript, the JVM, .NET, Python, and Ruby.
All six packages run the same WebAssembly module, written in Rust, so the mock answers the same way in each language.

The repository is [conao3/wasm-wasmo](https://github.com/conao3/wasm-wasmo), under the Apache-2.0 license.
This post uses 0.1.1, the version on each language's registry.

Another AWS mock I wrote, [bunsai](https://s.conao3.com/blog/2026/2653f0), listens on port 4566 as a separate server process, while wasmo runs inside the test process.

# Try it

In Python, you install it with `pip install wasmo boto3`.
A boto3 client you create inside `wasmo.mock_aws()` sends its requests to the mock.

The script below runs one mock: when an object lands in an S3 bucket, S3 invokes a Lambda function, and the function writes the object's key to a DynamoDB table.

```python
import boto3
import wasmo

with wasmo.mock_aws() as aws:
    s3 = boto3.client("s3")
    ddb = boto3.client("dynamodb")
    lam = boto3.client("lambda")

    ddb.create_table(
        TableName="uploads",
        KeySchema=[{"AttributeName": "key", "KeyType": "HASH"}],
        AttributeDefinitions=[{"AttributeName": "key", "AttributeType": "S"}],
        BillingMode="PAY_PER_REQUEST",
    )

    def on_upload(event, context):
        for record in event["Records"]:
            key = record["s3"]["object"]["key"]
            boto3.client("dynamodb").put_item(
                TableName="uploads", Item={"key": {"S": key}}
            )
        return {"ok": True}

    aws.register_function("on-upload", on_upload)
    fn = lam.create_function(
        FunctionName="on-upload",
        Runtime="python3.12",
        Role="arn:aws:iam::000000000000:role/lambda",
        Handler="index.handler",
        Code={"ZipFile": b"unused"},
    )

    s3.create_bucket(Bucket="photos")
    s3.put_bucket_notification_configuration(
        Bucket="photos",
        NotificationConfiguration={
            "LambdaFunctionConfigurations": [
                {"LambdaFunctionArn": fn["FunctionArn"], "Events": ["s3:ObjectCreated:*"]}
            ]
        },
    )

    s3.put_object(Bucket="photos", Key="cat.jpg", Body=b"...")
    print(ddb.get_item(TableName="uploads", Key={"key": {"S": "cat.jpg"}})["Item"])
```

```console
$ python demo.py
{'key': {'S': 'cat.jpg'}}
```

wasmo ignores the code you pass to `CreateFunction` and calls the Python function you registered under the same name with `register_function`.
S3 delivers the notification during the `PutObject` call, so the item is in DynamoDB by the time `put_object` returns.

wasmo calls your registered function at a point where the mock can take the next request, so the function can send requests to the same mock.
I wrote the same flow with the AWS SDK for JavaScript v3 and `@conao3/wasmo`, and `GetItem` returned the same item.

On my PC with an Intel Core Ultra 5 225U, I measured the Python package: the first request of a process took 0.6 to 1.0 seconds because it includes compiling the module.

Later requests took 2ms or less each.
Creating a new mock and getting its first response took 9ms, so you can create a fresh mock for each test.


# How it works

The AWS SDK of each of these six languages lets you replace its HTTP client, so wasmo uses the AWS wire protocol itself as the boundary between languages.

```text
your language's AWS SDK
  └─ HTTP client adapter (a few hundred lines per language)
       └─ WebAssembly runtime (Go: wazero, JVM: Chicory, JS: built-in, Ruby: wasmtime-rb, Python/.NET: wasmtime)
            └─ wasmo.wasm (Rust, wasm32-unknown-unknown)
```

The adapter turns the request the SDK built into a JSON of the method, URL, and headers plus the body bytes, passes them to the module's `wasmo_handle`, and hands the response back to the SDK.
The SDK still signs, retries, checks checksums, and parses responses, so your test runs the same SDK code it runs against real AWS.

The module needs no WASI and imports three host functions: a clock, a random source, and a Lambda invocation.
The state lives in a WebAssembly instance, and each mock gets its own instance, so tests that run in parallel keep their state apart.

When a response has to wait for a Lambda handler, the module returns an `await` marker in place of the response, and the adapter runs the registered function, passes the result to `wasmo_complete`, and repeats this until nothing is left to wait for.

# How wasmo differs from bunsai

bunsai and wasmo both mock AWS, and they run in different places.

bunsai is a server written in Bun that serves the AWS gateway and a dashboard on port 4566, so besides the SDKs, the AWS CLI and Terraform can use it once you point their endpoint at it.

It covers 146 services.
bunsai's Lambda starts the language runtime on the host, such as Python or Ruby, and runs your function code as it is.

wasmo runs inside the test process and replaces only the SDK's HTTP client, so a test creates a mock, uses it, and closes it.

It covers 19 services.
wasmo's Lambda calls a function you registered in your test's language in place of running your function code.

I check the behavior of wasmo's services by replaying bunsai's parity fixtures, whose expectations come from real AWS, and the [Conformance section of the README](https://github.com/conao3/wasm-wasmo#conformance) describes the method.

Use bunsai when you want the AWS CLI or Terraform or want to see the state on a dashboard, and use wasmo when you want everything to stay inside your language's tests.


# Supported services

0.1.1 answers the following 19 services.

-   Identity, keys, and secrets: STS, IAM, KMS, Secrets Manager, SSM Parameter Store
-   Messages and streams: SQS, SNS, EventBridge, Kinesis, Data Firehose
-   Data: S3, DynamoDB, DynamoDB Streams
-   Monitoring: CloudWatch, CloudWatch Logs
-   Functions and APIs: Lambda, Step Functions, API Gateway REST APIs and HTTP APIs

Services also deliver to each other inside the mock, along routes such as these.

-   SNS to SQS and Lambda
-   EventBridge to SQS, SNS, Lambda, and Step Functions
-   S3 notifications to SQS, SNS, EventBridge, and Lambda

Step Functions interprets the state machine definition inside the mock, and a task that calls Lambda waits for your registered function to return, so `StartSyncExecution` returns the output after your function has run.
The [Coverage section of the README](https://github.com/conao3/wasm-wasmo#coverage) lists the operations each service supports and all the delivery routes.

The README marks the project as early development.
In the repository's tests, the Go adapter covers each service in depth, and the other five languages run at least one end-to-end scenario per service through their SDKs.
