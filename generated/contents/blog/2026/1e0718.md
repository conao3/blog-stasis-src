Title: git fetch is Turing complete
Date: 2026-11-03
Draft: true
Lang: en


This is a program:

```console
$ git fetch loop
```

No hook runs, no alias starts a shell, and no `while` loop wraps Git.
One `git fetch` reads `.git/config`, renames a single ref again and again, and stops when the computation is done.
With the right config, `git fetch` can compute anything a Turing machine can.

Nicolas Seriot recently showed that curl 8.12 to 8.16 was accidentally Turing complete: its configuration files could run a two-counter Minsky machine ([How curl was accidentally Turing-complete for nine months](https://seriot.ch/computation/curl.html)).
Git can do the same without hooks, aliases, or scripts.
I did not find this myself; Claude Opus 5.5 did, and that story is at the end of this post.

The code is at [conao3/bash-git-minsky](https://github.com/conao3/bash-git-minsky).
`git-minsky` compiles a small program into a repository, and plain Git runs it.

# The machine to build

A two-counter Minsky machine has two counters, `a` and `b`, that hold non-negative integers, and a numbered list of instructions of three kinds.

-   `inc r next`: add one to counter `r` and go to instruction `next`.
-   `dec r next zero`: if `r` is positive, subtract one and go to `next`; otherwise go to `zero`.
-   `halt`: stop.

This is `examples/double.prog`, the program in the figure.
Instruction 1 takes one from `a`, instructions 2 and 3 add two to `b`, and the machine halts when `a` reaches zero.

```text
1 dec a 2 H
2 inc b 3
3 inc b 1
H halt
```

The rule on the Git side is strict.
Git has many ways to run a program: hooks, aliases that start with `!`, clean and smudge filters, diff drivers, `core.editor`, `core.pager`, and credential helpers.
None of them are allowed here.
The machine may only use Git's own behavior.


# Memory: one ref name

The whole machine lives in the name of a single ref.

![img](/img/1e0718-ref-name.svg)

`refs/A/s3xaaybz` is instruction `3` with `a = 2` and `b = 1`.
Each counter is written in unary, and the markers `x`, `y`, and `z` show where the counters start and end, so an empty counter is still visible: `refs/A/s1xaaayz` has `b = 0`.
Every ref points at the same empty commit; only the names matter.
The slot `A` is explained two sections below.


# Instructions: refspecs are rewrite rules

The repository has a remote called `self` whose URL is `.`, the repository itself.
A glob refspec such as `+refs/A/s1x*:refs/B/s2xa*` matches a ref name, keeps the part matched by `*`, and replaces the fixed text around it.
That is exactly what a counter machine needs: add or remove one letter at either end of a counter, and change the instruction number.

The zero test is pattern matching.
`refs/A/s1xa*` matches only when `a` is positive, and `refs/A/s1xy*` matches only when `a` is zero.


# One step takes two fetches

The instruction refspecs read from `refs/A` and write to `refs/B`.
`self` has one more refspec, `+refs/B/*:refs/A/*`, and `remote.self.prune = true`.
A fetch from `self` sees the refs that existed before the fetch, writes every destination, and prunes the destination refs that no source produced.
So the ref moves to `refs/B` on one fetch and back to `refs/A` on the next.

![img](/img/1e0718-two-fetches.svg)

Two fetches from `self` perform one step of the machine, which is one arrow in the first figure.


# Clock: a remote group that contains itself

Git can fetch a group of remotes with `git fetch <group>`, and a group may list itself.

```conf
[remotes]
        loop = self
        loop = loop
```

`git fetch loop` fetches `self`, then fetches the group `loop` again by starting a new `git fetch` process.
That is the clock.
No shell `while` is involved; a single `git fetch loop` runs the program to the end.


# Halt: a broken include

The machine still has to stop.
The configuration ends with `include.path = refs/H`.
Git resolves this path relative to `.git/` and silently skips an include file that does not exist.

The `halt` instruction writes one more ref, `refs/H/<counters>`.
With the files ref backend, that creates the directory `.git/refs/H`.
From that moment Git can no longer read `.git/config`, the next nested `git fetch` fails, and the whole chain unwinds.


# The whole program

`git-minsky` compiles `double.prog` into the `.git/config` below.
The gray labels on the left show which instruction each refspec implements.

![img](/img/1e0718-git-config.svg)

Here is the run with `a = 3`.
The two environment variables keep my own Git configuration out of the experiment.

```console
$ export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1
$ bin/git-minsky machine create-repository \
    --repository-path /tmp/m --program file://examples/double.prog --counter-a 3
{"RepositoryPath":"/tmp/m","Ref":"refs/A/s1xaaayz","RefspecCount":7}
$ git -C /tmp/m fetch loop
Fetching self
From .
 - [deleted]         (none)          -> refs/A/s1xaaayz
 * [new ref]         refs/A/s1xaaayz -> refs/B/s2xaayz
Fetching loop
Fetching self
From .
 - [deleted]         (none)         -> refs/B/s2xaayz
 * [new ref]         refs/B/s2xaayz -> refs/A/s2xaayz
...
warning: unable to access '.git/refs/H': Is a directory
fatal: bad config line 24 in file .git/config
error: could not fetch loop
...
$ bin/git-minsky machine describe-state --repository-path /tmp/m
{"State":"H","CounterA":0,"CounterB":6,"Halted":true}
```

The fetch log is the execution trace: every `[new ref]` line is one rename, and the `refs/A` names in it are the boxes of the first figure.


# Limits

This is Turing complete in the same idealized sense as the curl construction, and the real limits are worth stating.

-   Every step nests two more `git fetch` processes. A program that never halts stopped after 1,812 fetches (three minutes) on my Linux machine, with `unable to fork` and `Argument list too long`.
-   The files ref backend stores a ref as a file, so a ref name has at most 255 bytes, and `a + b` stays below about 250. The reftable backend removes that limit, but the halting trick needs the files backend.
-   For a local URL, Git starts `git-upload-pack` through `/bin/sh -c`. The shell only starts Git, but it is a process outside Git.


# Security impact

I see none.
The whole program lives in `.git/config`, and `git clone` never copies that file, so a remote repository cannot plant it; a remote only sends refs and objects, and the local refspecs decide what happens to their names.
Anyone who can write `.git/config` can already run any command through `core.hooksPath`, `core.fsmonitor`, or an alias that starts with `!`, and the SECURITY section of `git(1)` says so.
The worst this construction can do is fill the machine with nested `git fetch` processes, which the person who wrote the config could also do with a shell loop.


# How Claude Opus 5.5 found it

It started with a plain question to Claude Code: are there other stories like curl being Turing complete?
Opus 5.5 came back with the well-known list: sed, sendmail.cf, the C preprocessor, PowerPoint, Magic: The Gathering, and, most recently, GNU find.
Then I typed, more or less, "find new examples, this stuff is really fun on the internet", and a moment later "use agents while you explore".
That was the whole brief.

Opus 5.5 did not start with Git.
It first went through dozens of everyday tools, looking for the three things curl had: state that can be rewritten, a way to branch, and a way to repeat, all without starting a shell.
Most tools fail at the third one.
ssh\_config stops its includes at a fixed depth, Prometheus relabeling runs each rule once, and Terraform does not allow a module to call itself.
tmux had all three, but willhbr had already proved it Turing complete in 2024, so it was out.

Two candidates survived the screening, and each got its own agent.

-   Web server rewrite rules: Apache's `[N]` flag restarts the rule set after every rewrite, which turns the rules into a string rewriting system. nginx went to the same agent.
-   Git: its configuration has includes and conditions, and its refspecs rename refs.

A third agent got everything else: list more candidates, screen them the same way, and build whichever looked best.
Each agent had the same rule: no shell escapes, no embedded scripting language, only the tool's own features, and the result has to actually run.

The Git agent tried the obvious parts of Git first, and each of them lacked state that can change, a loop, or both.

-   `include.path` and `includeIf` only read configuration, and Git stops at an include depth of 10.
-   Aliases without `!` expand to one Git command, and Git detects alias loops.
-   The todo list of `git rebase -i` only moves forward. `label` and `reset` move `HEAD` but not the position in the list, and a conflict stops the rebase instead of branching.
-   Revision syntax, `for-each-ref --format` with `%(if)`, and mailmap read state but never write it.

The fetch refspec was the one place where Git reads a name, rewrites it by a pattern, and writes it back, and a remote group gives it a loop.
About fourteen minutes after it started, the agent reported a working two-counter Minsky machine, the measured recursion limit, and the caveat about `/bin/sh`.

The other agents came back with results too.
Apache's `mod_rewrite` worked as well, but it turned out to be known: s3lph built a binary adder with it in 2020.
nginx stops after 10 rewrites, a limit compiled into the binary.
The third agent made ImageMagick compute Rule 110 in a single `magick` command, and confirmed that GNU units rejects recursive definitions.

When I asked whether any of this was actually new, Opus 5.5 searched again and reported prior art where it existed instead of claiming everything.
For the Git construction it found nothing, which is not proof that nobody has done it before; if you know of earlier work, please tell me.
Opus 5.5 also wrote `git-minsky`, its tests, and the first draft of this post.
Every command output in this post comes from an actual run, pasted as is.
